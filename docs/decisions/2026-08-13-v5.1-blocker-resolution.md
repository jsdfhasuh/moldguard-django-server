## 1. 幂等机制

保留 6 个业务模型，并增加 1 个技术基础设施模型：

```text
ClientRequestRecord
```

字段：

```text
client_request_id     primary key
action
object_id
request_hash
response_status
response_json
created_at
```

所有写 API 必须提供 `client_request_id`；HTML 报工表单使用 `submission_id`，服务层映射为同一幂等机制。

规则：

```text
相同ID + 相同请求内容 → 返回第一次保存的响应，并标记 replayed=true
相同ID + 不同请求内容 → CLIENT_REQUEST_CONFLICT
失败响应不持久化为成功结果
```

因此当前模型口径为：

```text
6个业务模型 + 1个幂等基础设施模型
```

## 2. 注塑模次与时间同时触发

同一模具、同一 `cycle_version` 只允许存在一张开放的正式保养工单。

当模次规则与 `INJ-TIME-2M` 同时达到时：

```text
创建一条Alert
创建一张WorkOrder
primary_rule_id = 模次规则ID
matched_rule_ids_json = [模次规则ID, "INJ-TIME-2M"]
trigger_reason 同时记录两个触发条件
work_order_type = CYCLE_COUNT_MAINTENANCE
```

优先级：

```text
模次触发 > 时间触发
```

只有时间条件达到时，工单类型才是 `CYCLE_TIME_MAINTENANCE`。

正式保养去重键：

```text
FORMAL_MAINTENANCE:{mold_id}:{cycle_version}
```

## 3. 工单动作与状态副作用

| 动作 | 允许来源状态 | 目标状态 | 关键副作用 |
|---|---|---|---|
| `assign` | `PENDING_ASSIGNMENT` | `ASSIGNED` | 保存被派工人和派工时间 |
| `start` | `ASSIGNED` | `IN_PROGRESS` | 保存开工时间；该步骤可选 |
| `pause` | `IN_PROGRESS` | `PAUSED` | 保存暂停开始时间 |
| `resume` | `PAUSED` | `IN_PROGRESS` | 累加暂停秒数 |
| 正常报工 | `ASSIGNED` / `IN_PROGRESS` | `COMPLETED` | 创建履历、按矩阵复位、关闭Alert |
| 异常报工 | `ASSIGNED` / `IN_PROGRESS` / `PAUSED` | `ABNORMAL_REPORTED` | 不创建最终履历、不关闭Alert、不复位 |
| `continue-processing` | `ABNORMAL_REPORTED` | `IN_PROGRESS` | 清空本轮后续动作，保留异常历史 |
| `create-repair-task` | `ABNORMAL_REPORTED` | 原单 `REPAIR_LINKED` | 创建 `REPAIR_TASK` 子工单 |
| 修模子工单正常报工 | `ASSIGNED` / `IN_PROGRESS` | 子单 `COMPLETED` | 子单不复位；原单恢复 `IN_PROGRESS` |

一天版本不实现通用取消接口。避免取消后 Alert、去重键和重新建单产生额外状态分支。

正常报工允许从 `ASSIGNED` 直接提交，以支持“邮件链接直接报工”；不强制先调用 `start`。

`PAUSED` 状态不能正常报工，必须先恢复；异常报工允许从 `PAUSED` 提交，服务器在异常报工时间自动结束当前暂停段。

## 4. 无鉴权报工身份边界

报工页面不要求输入员工编号，不接受客户端声明报工人。

服务器直接使用：

```text
work_order.assignee
```

作为报工人员并在页面中只读展示。

当前演示身份机制为：

> 持有派工邮件中的报工链接即可提交该工单。本服务器只保证报工与已派工人员的逻辑关联，不提供真实身份认证。

CSRF 用于保护浏览器表单提交，但不代表员工身份认证。

## 5. 候选人员与负荷口径

一天版本采用确定性、固定演示口径：

```text
required_skill = mold_type
Employee.skills_json 必须包含 INJECTION 或 SHEET_METAL
current_load 为DEMO固定比例，不由工单自动增减
```

候选条件：

```text
available = true
on_duty = true
email 非空
current_load < 0.8
skills_json 包含 mold_type
```

排序：

```text
同产线优先
→ current_load升序
→ employee_id升序
```

不计算技能百分比，不维护人员最大容量，不因派工、完成或异常修改 `current_load`。

## 6. 标准工时与完成时间

`WorkOrder` 增加：

```text
standard_hours       nullable Decimal
required_finish_at   nullable DateTime
```

来源为显式 DEMO 配置：

```text
data/demo/work_order_defaults.json
```

查找顺序：

```text
mold_id专用配置
→ rule_id配置
→ 无配置则返回null
```

系统不生成未经配置的标准工时。统计接口对缺失标准工时的工单只统计实际工时，并返回：

```text
standard_hours_coverage
```

## 7. 知识包冻结

`WorkOrder` 增加：

```text
knowledge_package_hash
knowledge_locked_at
```

知识包写入规则：

```text
email_status != SENT 且尚未报工 → 允许新增或覆盖
email_status == SENT → 禁止覆盖，返回 KNOWLEDGE_PACKAGE_LOCKED
已报工 → 禁止覆盖
```

哈希算法：

```text
对规范化JSON执行SHA-256
```

`email-context`、`email-result`、报工页面和报工响应必须携带相同的：

```text
knowledge_snapshot_version
knowledge_package_hash
```

邮件发送成功时锁定知识包。

## 8. 报工契约

报工契约升级为：

```text
REPORT-FORM-1.1
```

核心变化：

- 增加 `submission_id`；
- 客户端不提交 `employee_id`；
- 明确 NORMAL / ABNORMAL 互斥校验；
- 明确字段长度、工时范围、HTTP 状态和成功响应；
- HTML 与 JSON 接口调用同一服务函数。

详细内容以 `docs/contracts/2026-08-13-mail-report-link-contract.md` 为准。

## 11. 最小过程追踪

为保留原参赛材料中的过程追踪能力，一天版本增加：

```http
POST /api/v1/tracking/scan
GET  /api/v1/work-orders/overdue
```

只识别：

```text
已派工/执行中工单超过 required_finish_at
异常报工超过配置时长仍未处理
```

Django返回结构化超时清单并写入事件；智能体平台负责生成催办或分析内容。无主管角色，不执行权限升级。
