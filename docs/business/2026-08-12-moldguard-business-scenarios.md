# MoldGuard 模具保养智能体业务场景说明

- **版本**：V2.0
- **日期**：2026-08-13
- **适用项目**：2026年珠海市职工劳动和技能竞赛“AI智能体操作与应用”
- **服务器定位**：无角色、无鉴权的 Django 测试服务器
- **知识库基线**：MoldGuard 模具保养知识库 V0.1
- **配套实施计划**：`docs/plans/2026-08-12-moldguard-django-implementation-plan.md`

---

## 1. 场景定位

MoldGuard 面向制造企业模具保养场景，在比赛环境中通过智能体平台和 Django 测试服务器共同演示：

```text
模具提醒
→ 工单创建
→ 人员选择与派工
→ 点检知识随邮件下发
→ 执行与点检
→ 验收或转修模
→ 周期复位
→ 工时分析
```

系统分工：

```text
智能体平台
= 对话 + 工作流 + 知识库/RAG + LLM + 邮件

Django测试服务器
= 模拟数据 + 规则 + 工单 + 状态 + 点检 + 统计
```

Django 不设置主管角色、用户登录或接口鉴权。业务中的“确认”“派工”“验收”都由平台操作人员在演示流程中触发，Django只检查业务状态和数据完整性。

---

## 2. 参与对象

这些对象只是业务场景标签，不是 Django 权限角色。

| 对象 | 场景作用 |
|---|---|
| 智能体平台 | 对话、工作流、知识检索、邮件和结果展示 |
| Django测试服务器 | 模拟模具、人员、工单、状态和统计 |
| 平台操作人员 | 在演示中选择人员、提交点检和选择验收结果 |
| 模拟保养人员 | 作为派工候选和邮件收件人 |
| 测试邮箱 | 接收任务和点检知识邮件 |

Django 不验证操作人员是否为主管、计划员或管理员。

---

## 3. 当前已确认规则

### 3.1 自动保养提醒

钣金和注塑模具当前不区分一级、二级、三级保养：

| 开发吨位 | 自动提醒周期 |
|---:|---:|
| `<1000T` | 每累计生产50,000模次 |
| `>=1000T` | 每累计生产30,000模次 |

### 3.2 每2个月提醒

当前适用于注塑模具：

```text
从cycle_baseline_time起每2个自然月
→ 只生成提醒
→ 不自动创建工单
→ 不自动派工
```

### 3.3 周期复位

以下事件复位周期：

```text
保养完成
修模完成
换镶件完成
有效历史记录导入
```

## 5. S01 查询模具和保养状态

用户输入：

```text
查询MOLD-2024-0891当前是否需要保养
```

平台调用：

```http
GET /api/v1/molds/{mold_id}/maintenance-status
```

Django返回：

- 模具编号和名称；
- 模具类型；
- 开发吨位；
- 当前累计模次；
- 周期基线模次；
- 当前周期模次；
- 适用阈值；
- 剩余或超期模次；
- 当前提醒状态；
- 下一次2个月提醒时间（注塑模具）。

平台根据这些事实生成自然语言说明。

---

## 6. S02 执行今日巡检

平台每日定时或手动调用：

```http
POST /api/v1/alerts/scan
```

Django：

1. 读取所有参与扫描的模拟模具；
2. 根据开发吨位选择30,000或50,000模次阈值；
3. 计算周期模次；
4. 生成模次到期提醒；
5. 对注塑模具计算2个月信息提醒；
6. 防止重复提醒；
7. 返回提醒清单。

模次到期提醒可以进入工单流程；2个月提醒只用于通知。

---

## 7. S03 注塑模具每2个月提醒

满足：

```text
current_time >= cycle_baseline_time + 2 calendar months
```

Django创建：

```text
alert_type = MAINTENANCE_TIME_REMINDER
business_action = REMIND_ONLY
```

平台发送提醒，但不得自动调用创建工单接口。

提醒内容应说明：

> 本提醒仅表示距当前周期基线已满2个月，不表示模次保养条件已经达到。

---

## 8. S04 创建保养工单

平台选择一条模次到期提醒后调用：

```http
POST /api/v1/work-orders
```

Django：

- 校验提醒存在；
- 校验开发吨位和周期数据有效；
- 检查同一模具是否已有未关闭工单；
- 创建 `PENDING_ASSIGNMENT` 工单；
- 保存规则和模次快照。

没有主管确认角色。平台操作人员点击“创建工单”即可。

---

## 9. S05 查询候选人员并派工

平台调用：

```http
GET /api/v1/work-orders/{work_order_id}/candidates
```

候选条件：

```text
技能匹配率 >= 80%
当前负荷 < 80%
在岗且可用
邮箱已配置
同产线优先
```

平台操作人员选择候选人后调用：

```http
POST /api/v1/work-orders/{work_order_id}/assign
```

Django重新检查被选人员是否仍可用，然后保存派工结果。

Django不检查选择者是否为主管。

---

## 10. S06 点检知识随邮件下发

平台从 Django 获取：

```text
mold_type
trigger_rule_id
rule_version
knowledge_profile_code
knowledge_tags
```

平台检索：

- 保养项目；
- 注塑或钣金点检项；
- 安全注意事项；
- 验收标准；
- 异常处理参考。

平台回写知识快照：

```http
POST /api/v1/work-orders/{work_order_id}/knowledge-snapshot
```

平台发送邮件后回写：

```http
POST /api/v1/work-orders/{work_order_id}/notifications
```

Django不发送邮件。

历史3万/5万/10万分类周期和一保/二保/三保资料只能作为知识说明，不能覆盖当前30,000/50,000吨位规则。

---

## 11. S07 开工、暂停和恢复

平台直接调用：

```http
POST /api/v1/work-orders/{id}/start
POST /api/v1/work-orders/{id}/pause
POST /api/v1/work-orders/{id}/resume
```

Django：

- 校验工单状态；
- 记录时间；
- 保存暂停原因；
- 累计暂停时长；
- 写入工单时间线。

没有人员登录和身份校验。

---

## 12. S08 逐项点检和报完工

平台把知识库检索出的点检模板回写 Django。

每项结果：

```text
PASS
FAIL
NOT_APPLICABLE
```

约束：

- 所有适用项必须填写；
- FAIL必须填写异常；
- NOT_APPLICABLE必须填写原因；
- 未完成点检不能报完工。

报完工接口：

```http
POST /api/v1/work-orders/{id}/report-complete
```

报完工后进入 `PENDING_ACCEPTANCE`。

---

## 13. S09 验收、退回和转修模

平台根据点检和知识库验收要求展示三个操作：

```text
验收通过
退回继续处理
转修模
```

对应接口：

```http
POST /api/v1/work-orders/{id}/accept
POST /api/v1/work-orders/{id}/reject
POST /api/v1/work-orders/{id}/transfer-to-repair
```

Django只检查状态和点检完整性，不检查操作者角色。

转修模 P0 只创建 `RepairReferral`，不实现完整维修工单。

---

## 14. S10 保养完成后周期复位

验收通过后，Django在同一事务中：

1. 工单设为 `COMPLETED`；
2. 创建保养履历；
3. 创建 `CycleResetEvent(MAINTENANCE_COMPLETED)`；
4. 更新周期基线模次和时间；
5. 创建新周期版本；
6. 重算下一模次到期点；
7. 重算注塑模具下一次2个月提醒；
8. 关闭旧周期未处理提醒。

---

## 15. S11—S13 其他周期复位

### 修模完成

```http
POST /api/v1/molds/{mold_id}/repair-completed
```

### 换镶件完成

```http
POST /api/v1/molds/{mold_id}/insert-replaced
```

### 历史记录导入

```http
POST /api/v1/molds/{mold_id}/history-records
```

有效历史记录使用实际业务发生模次和时间。早于当前基线的记录默认只归档，不倒退周期。

## 16. S14 工时和完成率分析

Django提供：

```http
GET /api/v1/analytics/summary
GET /api/v1/analytics/work-hours
GET /api/v1/analytics/order-completion
GET /api/v1/analytics/overdue-orders
GET /api/v1/analytics/mold-history
```

平台通过自然语言解释：

- 工单数量；
- 已完成数量；
- 完成率；
- 派工至报工总历时；
- 等待开工时间；
- 实际执行时间；
- 暂停时间；
- 超时工单。

Django只提供数据，LLM负责说明。

## 18. 参赛演示流程

建议5—7分钟：

1. 执行今日巡检；
2. 展示一套黄色或到期模具；
3. 创建工单；
4. 查询候选人员；
5. 平台操作人员选择并派工；
6. 检索点检知识并发送邮件；
7. 展示邮件；
8. 开工、暂停和恢复；
9. 提交点检并报完工；
10. 选择验收通过；
11. 展示周期复位；
12. 查询工时和完成率；
13. 快速展示点检失败转修模异常路径。

---

## 19. 答辩说明

> 本项目中的Django是一台比赛测试服务器，所以没有建设主管账号、人员登录和接口鉴权。平台操作人员可以直接触发派工和验收，但Django仍保存工单状态、点检结果、周期基线和工时数据。这样既保留原方案的完整业务演示，又减少了与比赛无关的账号权限和安全部署工作。

---

## 20. 场景边界

测试服务器只使用模拟数据，不接入真实生产系统。以下能力不在本版范围：

- 企业身份和权限；
- 真实排产锁定；
- 真实MES/ERP写入；
- 完整修模流程；
- 备件和成本；
- 生产级安全、容灾和审计合规。
