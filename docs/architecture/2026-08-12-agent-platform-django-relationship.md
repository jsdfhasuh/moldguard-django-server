# 智能体平台与 Django 服务器关系说明

- **版本**：V1.0
- **日期**：2026-08-12
- **适用项目**：MoldGuard 模具保养智能预警与管理智能体
- **配套计划**：`docs/plans/2026-08-12-moldguard-django-implementation-plan.md`

---

## 1. 一句话说明

> **智能体平台负责“理解、检索、生成、编排和通知”，Django 负责“数据、规则、事务、状态和审计”。**

智能体平台是面向用户的智能交互与流程编排入口；Django 是系统可信业务事实的来源，也是工单全生命周期的状态中心。

两者共同完成：

```text
预警
→ 工单
→ 派工
→ 知识随单邮件
→ 过程追踪
→ 报工验收
→ 归档分析
```

---

## 2. 为什么需要两套系统配合

单独依靠智能体平台，适合完成自然语言交互、知识库检索、LLM 内容生成和邮件发送，但不适合独立承担：

- 精确模次计算；
- 保养标准版本匹配；
- 工单去重；
- 角色权限；
- 合法状态跳转；
- 并发事务；
- 实际工时计算；
- 业务审计。

单独依靠 Django，可以稳定管理业务数据和流程状态，但无法充分发挥：

- 自然语言交互；
- RAG 知识检索；
- 预警报告生成；
- 催办与异常话术；
- 邮件正文组织；
- 对话式数据分析。

因此，本项目将“智能能力”和“业务系统能力”拆分，由两者通过 HTTPS JSON API 协作。

## 4. 两者职责矩阵

| 业务环节 | 智能体平台 | Django |
|---|---|---|
| 用户输入 | 理解自然语言和意图 | 不负责自然语言理解 |
| 模具查询 | 调用 API、展示结果 | 查询并返回模具事实 |
| 保养标准 | 根据结果组织说明 | 匹配精确标准和版本 |
| 健康评分 | 展示和解释 | 按冻结公式计算 |
| 预警等级 | 生成自然语言报告 | 计算并保存红黄绿结果 |
| 定时巡检 | 每日 08:00 触发工作流 | 执行扫描并保存预警记录 |
| 工单生成 | 收集确认、调用接口 | 创建、去重并保存工单 |
| 候选人员 | 展示并让主管确认 | 按技能、负荷、产线和等级筛选 |
| 最终派工 | 接收主管选择、调用接口 | 重新校验并保存派工结果 |
| 点检知识 | 检索知识库正文 | 返回知识画像编码和过滤标签 |
| 知识随单 | 组装任务和知识 | 保存本次实际使用的知识快照 |
| 邮件发送 | 生成并发送邮件 | 不发送邮件 |
| 邮件记录 | 回写发送结果 | 保存发送状态和平台消息 ID |
| 开工/暂停/报工 | 接收用户操作并调用接口 | 校验状态、权限和时间，保存事件 |
| 验收 | 检索验收标准、引导主管操作 | 保存验收、归档并更新模具履历 |
| 异常追踪 | 生成异常分析与催办话术 | 识别超时、保存异常和升级记录 |
| 工时分析 | 理解问题并生成结论 | 提供可复算的结构化统计数据 |
| 审计 | 传递操作人和请求 ID | 记录业务操作、前后状态和结果 |

## 5. 可信事实原则

下列内容必须以 Django 返回为准，智能体平台和 LLM 不得自行生成或修改：

- 模具编号、名称、类型、等级、位置和当前状态；
- 当前累计模次和上次保养模次；
- 保养标准模次、标准工时和标准版本；
- 使用率、健康评分和预警等级；
- 工单编号、状态、优先级和截止时间；
- 人员编号、技能、负荷、在岗状态和邮箱；
- 最终派工结果；
- 开工、暂停、恢复、报工和验收时间；
- 实际工时、暂停时长和工时偏差；
- 工单完成率、超时数量和人员负荷。

智能体平台可以解释这些事实，但不能覆盖 Django 的业务结果。

---

## 6. 知识内容原则

下列内容主要由智能体平台知识库提供：

- 一、二、三级保养项目；
- 操作步骤；
- 安全注意事项；
- 验收标准；
- 故障案例；
- 备件说明；
- 异常处理建议；
- 最佳实践。

Django 不保存完整知识库正文，但保存：

- `knowledge_profile_code`；
- 来源文档名称；
- 文档版本；
- 章节或片段标识；
- 检索标签；
- 内容摘要；
- 内容哈希；
- 检索时间。

这样既避免在 Django 中重复建设知识库，又能证明某张工单当时使用了哪一版知识。

## 7. 完整交互时序

### 7.1 预警扫描

```text
智能体平台
  │ POST /api/v1/alerts/scan
  ▼
Django
  │ 查询模具、匹配标准、计算健康评分
  │ 保存预警记录
  ▼
智能体平台
  │ 获取黄色/红色清单
  │ LLM生成预警报告
  │ 可发送预警通知
```

### 7.2 创建工单

```text
智能体平台
  │ 用户/主管确认创建
  │ POST /api/v1/work-orders
  ▼
Django
  │ 校验预警
  │ 检查重复未关闭工单
  │ 保存模具与标准快照
  │ 创建 PENDING_ASSIGNMENT 工单
  ▼
智能体平台
  │ 展示工单编号和详情
```

### 7.3 候选人员与最终派工

```text
智能体平台
  │ GET /work-orders/{id}/candidates
  ▼
Django
  │ 计算技能匹配、负荷、同产线和技师等级
  │ 返回候选人与原因
  ▼
智能体平台
  │ 展示候选人
  │ 主管最终确认
  │ POST /work-orders/{id}/assign
  ▼
Django
  │ 再次校验人员资格
  │ 保存派工记录
  │ 工单状态更新为 ASSIGNED
```

候选查询不是派工结果。只有 Django 成功接受 `assign` 请求后，才表示派工生效。

### 7.4 知识检索和邮件发送

```text
智能体平台
  │ GET /work-orders/{id}/knowledge-context
  ▼
Django
  │ 返回 knowledge_profile_code、标签和标准版本
  ▼
智能体平台
  │ 检索点检要求、步骤、安全事项和验收标准
  │ POST /work-orders/{id}/knowledge-snapshot
  ▼
Django
  │ 保存本次知识快照
  ▼
智能体平台
  │ 组装并发送派工邮件
  │ POST /work-orders/{id}/notifications
  ▼
Django
  │ 保存邮件发送状态
```

邮件由智能体平台发送；Django 只负责记录结果。邮件失败不回滚已经生效的派工。

### 7.5 执行与报工

```text
保养人员在平台发起开工
  │ POST /work-orders/{id}/start
  ▼
Django：ASSIGNED → IN_PROGRESS

保养人员暂停
  │ POST /work-orders/{id}/pause
  ▼
Django：IN_PROGRESS → PAUSED，记录原因和开始时间

保养人员恢复
  │ POST /work-orders/{id}/resume
  ▼
Django：PAUSED → IN_PROGRESS，计算暂停区间

保养人员报工
  │ POST /work-orders/{id}/complete
  ▼
Django：IN_PROGRESS → PENDING_ACCEPTANCE
```

### 7.6 验收与归档

```text
智能体平台检索验收标准
  │ 引导主管验收
  │ POST /work-orders/{id}/accept
  ▼
Django
  │ PENDING_ACCEPTANCE → COMPLETED
  │ 生成保养履历
  │ 更新模具上次保养模次和时间
  │ 关闭关联预警
  │ 计算工时偏差
```

验收不通过时：

```text
POST /work-orders/{id}/reject
PENDING_ACCEPTANCE → IN_PROGRESS
```

## 8. 关键接口关系

| 智能体平台动作 | Django 接口 | Django结果 |
|---|---|---|
| 执行今日巡检 | `POST /alerts/scan` | 保存并返回预警 |
| 查询待保养模具 | `GET /molds/due` | 黄色/红色清单 |
| 创建保养工单 | `POST /work-orders` | 新工单或重复工单错误 |
| 查询候选人员 | `GET /work-orders/{id}/candidates` | 候选人和匹配依据 |
| 确认派工 | `POST /work-orders/{id}/assign` | 已派工事实 |
| 获取知识检索标签 | `GET /work-orders/{id}/knowledge-context` | 知识画像和过滤条件 |
| 保存知识来源 | `POST /work-orders/{id}/knowledge-snapshot` | 知识快照 ID |
| 回写邮件结果 | `POST /work-orders/{id}/notifications` | 邮件审计记录 |
| 开工 | `POST /work-orders/{id}/start` | 状态变为执行中 |
| 暂停/恢复 | `POST /pause`、`POST /resume` | 暂停区间和时间线 |
| 报工 | `POST /complete` | 状态变为待验收 |
| 验收/退回 | `POST /accept`、`POST /reject` | 完成归档或退回执行 |
| 获取超时任务 | `GET /work-orders/overdue` | 催办和异常清单 |
| 查询统计 | `GET /analytics/*` | 结构化统计数据 |

## 9. 操作权限关系

智能体平台通过 `X-API-Key` 证明自己是受信任调用方，但每个写动作仍需传递具体操作人。

建议角色：

| 角色 | 允许操作 |
|---|---|
| `ADMIN` | 管理演示数据和全部业务操作 |
| `MOLD_SUPERVISOR` | 确认预警、创建工单、派工、改派、验收、取消和升级 |
| `MAINTAINER` | 查询本人任务、开工、暂停、恢复、报工和提交异常 |
| `ANALYST` | 查询统计，不执行业务写入 |
| `PLATFORM_SERVICE` | 按工作流调用接口，但动作权限仍取决于 actor_id |

用户在对话中说“我是某某”不能直接成为身份依据。Django 必须根据传入的 `actor_id` 查询本地操作人并校验角色。

## 10. 幂等与重试关系

智能体平台可能因为网络超时自动重试。所有写接口都必须携带：

```http
Idempotency-Key: <stable-key>
```

同一次业务动作重试时必须使用相同键。

示例：

```text
scan-2026-08-12-morning
create-alert-ALT-20260812-001
assign-WO-20260812-001-EMP-0012
start-WO-20260812-001
email-WO-20260812-001-v1
```

Django 对相同幂等键返回原结果，不重复创建预警、工单、派工或状态事件。

## 11. 失败处理原则

### 11.1 Django 请求失败

平台必须展示 Django 返回的明确错误，不得让 LLM 编造成功结果。

例如：

- `STANDARD_NOT_FOUND`：没有保养标准；
- `DUPLICATE_OPEN_WORK_ORDER`：已有未关闭工单；
- `INVALID_STATE_TRANSITION`：状态不允许；
- `STAFF_NOT_ELIGIBLE`：被选人员不满足条件；
- `PERMISSION_DENIED`：操作人无权限。

### 11.2 知识库无召回

- 工单和派工状态不受影响；
- 平台提示“未检索到适用点检知识”；
- 不发送没有安全要求和验收标准的正式任务邮件；
- 允许主管人工选择知识文件后继续。

### 11.3 邮件发送失败

- Django 中工单仍保持 `ASSIGNED`；
- 平台回写 `FAILED`；
- 平台可以重试发送；
- 重试只新增邮件尝试记录，不重复派工。

### 11.4 平台超时但 Django 已执行

平台使用原 Idempotency-Key 重试，Django 返回第一次执行结果。

出现冲突时，以权威系统的数据为准。

## 13. 比赛演示中的分工表达

答辩时可以这样说明：

> 我们没有让大模型直接管理生产业务数据。智能体平台负责理解用户需求、检索点检知识、生成任务说明和发送邮件；Django 服务器负责模具实时数据、保养规则、工单状态、人员资格、实际工时和审计。平台每次要创建工单、派工、开工或验收，都必须调用 Django 接口，由 Django 校验后才能生效。这样既发挥了 AI 的交互和知识能力，也保证了制造业务数据的准确性和流程可追溯性。

---

## 14. 不允许的实现方式

- LLM 自行生成模具模次、标准工时或员工编号；
- 平台显示“派工成功”但未调用 Django 派工接口；
- 平台发送邮件后不回写结果；
- Django 重复保存完整知识库；
- Django 直接调用大模型决定最终派工人；
- 用户仅通过自然语言声明身份即可执行主管操作；
- 状态跳转只在平台变量中保存而不写入 Django；
- 邮件发送失败时重复创建工单；
- 验收完成后不更新模具保养基准和履历。

## 15. 最终结论

智能体平台与 Django 的关系可以概括为：

```text
智能体平台 = 智能交互层 + 知识层 + 编排层 + 通知层
Django      = 业务数据层 + 规则层 + 事务层 + 状态层 + 审计层
```

智能体平台让系统“会理解、会检索、会表达、会通知”；Django 让系统“数据真实、规则确定、动作有效、状态一致、过程可追溯”。

只有两者共同工作，才能完整支撑原参赛材料中的模具预警、自动工单、智能派工、过程追踪、报工验收和工时分析。
