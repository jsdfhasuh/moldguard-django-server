# MoldGuard Django 虚拟业务服务器实现计划

- **状态**：待负责人审阅
- **版本**：V0.1
- **日期**：2026-08-12
- **目标仓库**：`moldguard-django-server`
- **默认分支**：`main`
- **计划性质**：比赛版实现基线，尚未进入编码阶段

---

## 1. 背景与关键决策

原始方案将系统拆分为模具预警、工单生成、过程追踪、工时分析和知识库五项核心能力，并设计了模具信息查询、保养条件判断、人员派工、工单流转、异常升级和知识检索流程。

本计划结合比赛平台实际能力，采用以下实施结构：

> **一个比赛智能体平台 + 一个 Django 外部虚拟业务服务器。**

关键决策如下：

1. 比赛平台已经具备邮件发送能力，因此 Django 不再实现 SMTP、邮件模板、附件生成、Mailpit、Celery 邮件任务和邮件重试。
2. 点检要求、操作步骤、安全事项和验收标准存放在比赛平台知识库中，由平台检索并随派工邮件发送。
3. Django 仅保存结构化业务数据，负责所有确定性计算、工单状态校验、候选人员筛选和统计。
4. 平台可以在邮件发送完成后，将发送结果回写 Django，形成可选的通知审计闭环。
5. 第一阶段使用模拟 MES、模拟人员池和模拟工单数据；接口契约保持稳定，后续可替换为真实 MES/ERP 适配器。

## 2. 项目目标

完成以下可稳定演示的业务闭环：

```text
用户查询模具或执行今日巡检
        ↓
比赛平台调用 Django 查询模具状态
        ↓
Django 计算保养周期使用率和预警等级
        ↓
平台根据 Django 返回的标签检索点检知识库
        ↓
平台生成预警报告和工单草稿
        ↓
Django 创建保养工单并返回候选人员
        ↓
主管确认派工
        ↓
平台将工单任务和点检知识通过邮件发送给保养人员
        ↓
平台调用 Django 记录开工、暂停、恢复、报工和验收
        ↓
Django 输出工时、完成率、超时工单和人员负荷统计
```

项目完成后，应具备以下能力：

- 查询单套模具基本资料和保养状态；
- 批量筛选黄色、红色待保养模具；
- 创建保养工单并防止重复创建；
- 根据技能、负荷、产线和技师等级返回候选人员；
- 经主管确认后完成派工；
- 执行工单状态机和异常校验；
- 记录完整操作时间线和审计日志；
- 为知识库检索返回稳定的标签和查询上下文；
- 可选记录比赛平台的邮件发送结果；
- 提供工时、完成率、超时和人员负荷统计。

## 3. 范围边界

### 3.1 Django 负责

- 模具台账；
- 当前累计模次和上次保养记录；
- 保养标准及版本；
- 保养周期使用率计算；
- 绿色、黄色、红色预警判断；
- 人员、班组、技能、技师等级、负荷和在岗状态；
- 工单创建、派工、开工、暂停、恢复、报工、验收和取消；
- 工单状态合法性校验；
- 候选人员筛选与排序；
- 工时、完成率、超时工单和人员负荷统计；
- API 认证、幂等、请求追踪和审计日志；
- 可选的邮件通知结果回写。

### 3.2 比赛平台负责

- 用户自然语言意图识别；
- 工作流编排；
- 定时或手动巡检触发；
- 点检知识库建设与检索；
- 根据业务数据生成预警报告；
- 主管确认交互；
- 将派工任务与点检知识组装成邮件；
- 邮件发送；
- 需要时调用 Django 回写邮件发送结果。

### 3.3 第一阶段不实现

- Django 自建向量数据库或 RAG；
- Django SMTP 邮件发送；
- Redis、Celery 和 Celery Beat；
- 真实企业微信或钉钉通知；
- 真实 MES/ERP 写入；
- 自动锁定生产排程；
- 大模型直接决定最终派工人员；
- 独立 Vue/React 管理前端；
- 复杂成本预测和备件采购；
- 未经业务确认的健康评分模型。

## 6. 核心数据模型

### 6.1 Mold：模具台账

建议字段：

- `mold_id`：模具编号，唯一；
- `mold_name`：模具名称；
- `mold_type`：注塑模具、钣金模具等；
- `mold_level`：模具等级；
- `mold_category`：模具类别；
- `cavity_count`：腔数；
- `current_count`：当前累计生产模次；
- `last_maintenance_count`：上次保养时累计模次；
- `last_maintenance_time`：上次保养时间；
- `primary_location`：一级位置；
- `secondary_location`：二级位置；
- `production_line`：所属产线；
- `status`：生产中、库存、维修、停用；
- `created_at`、`updated_at`。

### 6.2 MaintenanceStandard：保养标准

建议字段：

- `standard_id`；
- `mold_type`；
- `mold_level`；
- `maintenance_level`；
- `maintenance_threshold`：标准保养模次；
- `maintenance_days`：可选时间周期；
- `standard_hours`；
- `required_skills`；
- `version`；
- `effective_from`；
- `is_active`。

精确阈值、标准工时和规则版本必须保存在 Django 数据库中，不能仅依赖知识库检索。

### 6.3 Employee 与 Skill：人员及技能

建议模型：

- `Employee`；
- `Skill`；
- `EmployeeSkill`；
- `StaffAvailability`。

人员主要字段：

- 员工编号；
- 姓名；
- 邮箱；
- 班组；
- 所属产线；
- 技师等级；
- 当前负荷，范围 `0.00—1.00`；
- 是否在岗；
- 是否可派工。

### 6.4 MaintenanceAlert：预警记录

建议字段：

- 模具；
- 规则版本；
- 距上次保养运行模次；
- 标准阈值；
- 保养周期使用率；
- 预警等级；
- 计算时间；
- 处理状态；
- 关联工单。

### 6.5 WorkOrder：保养工单

建议字段：

- `work_order_id`；
- 模具；
- 保养标准；
- 保养等级；
- 预警等级；
- 优先级；
- 保养项目摘要；
- 标准工时；
- 要求完成时间；
- 派工员工；
- 当前状态；
- 创建、派工、开工、暂停、恢复、报工、验收时间；
- 暂停累计时长；
- 实际工时；
- 异常原因；
- 验收结果；
- 创建人和确认人。

### 6.6 WorkOrderEvent：工单时间线

每次业务动作写入事件：

- 工单；
- 事件类型；
- 原状态；
- 新状态；
- 操作人；
- 操作时间；
- 备注；
- `request_id`。

### 6.7 NotificationEvent：邮件发送结果（可选）

Django 不发送邮件，只在平台愿意回写时记录：

- 工单；
- 渠道，固定为 `EMAIL`；
- 收件人；
- 平台消息 ID；
- 发送状态；
- 发送时间；
- 使用的知识来源标题和版本；
- 失败原因；
- `request_id`。

### 6.8 AuditLog：审计日志

记录：

- 用户编号和角色；
- API 路径和动作；
- 业务对象；
- 请求 ID；
- 幂等键；
- 操作结果；
- 错误码；
- 来源 IP；
- 时间。

## 7. 预警规则

### 7.1 原方案缺口

原始材料使用健康评分判定红、黄、绿预警，并给出“93.25%使用率对应72分”的示例，但没有提供使用率到健康评分的完整公式、维度和权重。

因此第一版不能自行假设健康评分模型。

### 7.2 第一版暂定计算

```python
run_count_since_last = current_count - last_maintenance_count
maintenance_ratio = run_count_since_last / maintenance_threshold
```

暂定演示规则：

| 使用率 | 预警等级 | 动作 |
|---:|---|---|
| `< 90%` | 绿色 | 正常运行 |
| `90%—<100%` | 黄色 | 建议7日内安排保养 |
| `>= 100%` | 红色 | 建议立即安排，并请求主管确认是否影响排产 |

注意：

- 以上阈值是比赛演示适配值，不是原始材料已经确认的业务标准；
- 阈值必须配置化，不能硬编码；
- 原方案提出红色预警“强制锁定排产”，第一版不执行真实锁定，仅返回建议和确认要求；
- 若业务方提供正式健康评分公式，再增加可版本化的评分策略。

## 8. 候选人员与派工规则

Django 按确定性规则返回候选人，不让大模型凭空生成员工信息。

原方案给出的规则基线：

1. 技能匹配度不低于80%；
2. 当前负荷低于80%；
3. 同产线人员优先；
4. 高优先级模具优先高级技师。

### 8.1 第一版筛选顺序

1. 排除未在岗或不可派工人员；
2. 排除技能匹配度低于80%的人员；
3. 排除当前负荷不低于80%的人员；
4. 同产线人员优先；
5. 高优先级工单按技师等级降序；
6. 其余按当前负荷升序；
7. 返回候选人及每项推荐原因；
8. 最终派工必须由主管确认。

### 8.2 待确认项

原材料没有定义技能匹配度的计算方法和各规则权重。第一版采用“过滤 + 明确排序”，暂不构造复杂综合评分。

## 9. 工单状态机

```text
PENDING_ASSIGNMENT  待派工
        ↓ assign
ASSIGNED            已派工
        ↓ start
IN_PROGRESS         执行中
        ├─ pause  → PAUSED 已暂停
        │             └─ resume → IN_PROGRESS
        ↓ complete
PENDING_ACCEPTANCE  待验收
        ├─ reject → IN_PROGRESS
        ↓ accept
COMPLETED           已完成

待派工、已派工、执行中、已暂停可按权限进入 CANCELLED 已取消。
```

### 9.1 必须校验

- 待派工不能直接开工或报工；
- 未派工不能开工；
- 暂停必须填写原因；
- 已暂停不能直接报工；
- 未报工不能验收；
- 验收退回后回到执行中；
- 已完成工单不能重新派工或修改关键结果；
- 同一模具存在未关闭保养工单时，默认禁止重复创建；
- 每个状态动作都必须写入 `WorkOrderEvent`。

### 9.2 实际工时口径

建议使用：

```text
实际工时 = 报工时间 - 开工时间 - 暂停累计时长
```

原材料使用“报工时间 - 派工时间”，两者口径不同，正式实现前需业务负责人确认。

## 10. API 契约草案

### 10.1 通用约定

- 基础路径：`/api/v1`；
- 格式：`application/json`；
- 时间：带时区 ISO 8601；
- 认证：`X-API-Key`；
- 用户上下文：`X-User-Id`、`X-User-Role`；
- 请求跟踪：`X-Request-ID`；
- 写操作幂等：`Idempotency-Key`；
- 关键写操作请求体必须包含 `confirm: true`。

统一响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "request_id": "req-20260812-0001"
}
```

### 10.2 基础与模具接口

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/health` | 检查应用和数据库状态 |
| GET | `/molds` | 查询模具列表 |
| GET | `/molds/{mold_id}` | 查询模具详情 |
| GET | `/molds/{mold_id}/maintenance-status` | 查询保养计算和预警 |
| GET | `/molds/due` | 查询黄色、红色待保养模具 |
| POST | `/inspections/run` | 手动执行批量巡检并保存预警记录 |
| GET | `/maintenance-standards` | 查询保养标准 |

### 10.3 人员与派工接口

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/staff` | 查询人员池 |
| POST | `/staff/candidates` | 根据工单返回候选人员 |
| GET | `/staff/{employee_id}/work-orders` | 查询员工工单 |

### 10.4 工单接口

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/work-orders` | 创建工单 |

| POST | `/work-orders/{id}/assign` | 主管确认派工或改派 |

| POST | `/work-orders/{id}/complete` | 报工 |
| POST | `/work-orders/{id}/accept` | 验收通过或退回 |

### 10.5 统计与审计接口

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/analytics/summary` | 工单和工时总览 |
| GET | `/analytics/work-hours` | 人员、班组和车间工时 |

| GET | `/analytics/staff-load` | 人员负荷 |
| GET | `/audit-logs` | 按请求或业务对象查询审计日志 |

### 10.6 邮件结果回写接口（可选）

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/work-orders/{id}/notification-events` | 比赛平台回写邮件发送结果 |
| GET | `/work-orders/{id}/notification-events` | 查询通知记录 |

回写示例：

```json
{
  "channel": "EMAIL",
  "status": "SENT",
  "recipient": "zhangsan@example.com",
  "platform_message_id": "mail-20260812-001",
  "sent_at": "2026-08-12T15:30:12+08:00",

    {
      "document_name": "注塑模具一级保养点检标准",

```

该接口只用于审计，不负责发送邮件。

- 异常处理要求；
- 知识来源文档和版本。

平台必须使用 Django 返回的业务数据和知识库实际检索结果，不得让 LLM 自行修改模次、阈值、工时、员工或工单状态。

## 12. 认证、权限、幂等与错误处理

### 12.1 角色

| 角色 | 允许操作 |
|---|---|
| `ADMIN` | 管理全部数据和配置 |
| `SUPERVISOR` | 创建、派工、改派、验收、取消 |
| `MAINTAINER` | 查看本人任务、开工、暂停、恢复、报工 |
| `ANALYST` | 只读统计与工单查询 |
| `AGENT_PLATFORM` | 在用户上下文和权限范围内调用接口 |

### 12.2 安全要求

- API Key 存储在环境变量，不写入仓库；
- 写接口校验用户编号、角色和确认标记；
- 管理后台仅允许内部管理员访问；
- 生产数据库端口不开放公网；
- 日志不得记录 API Key；
- CORS 只允许比赛平台域名；
- 对关键接口设置限流；
- Django `DEBUG=False` 后再部署公网。

### 12.3 幂等

以下接口必须支持 `Idempotency-Key`：

- 创建工单；
- 派工；
- 开工；
- 暂停；
- 恢复；
- 报工；
- 验收；
- 通知结果回写。

平台重试时，Django 返回原操作结果，不重复创建记录。

### 12.4 关键错误码

- `MOLD_NOT_FOUND`；
- `STANDARD_NOT_FOUND`；
- `DUPLICATE_OPEN_ORDER`；
- `INVALID_STATE_TRANSITION`；
- `STAFF_NOT_FOUND`；
- `STAFF_NOT_QUALIFIED`；
- `STAFF_UNAVAILABLE`；
- `CONFIRMATION_REQUIRED`；
- `PERMISSION_DENIED`；
- `IDEMPOTENCY_CONFLICT`；
- `VALIDATION_ERROR`。

平台收到错误后必须展示接口事实，不能把失败描述成成功。

## 18. 风险与待确认事项

1. 注塑模具和钣金模具的准确保养阈值；
